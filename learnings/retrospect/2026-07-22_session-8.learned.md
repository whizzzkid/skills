## Session-8

### What worked
- Cross-verifying a lagging CI-status API against ground-truth sources (the pushed ref via `git ls-remote` and the CI provider's own build-by-branch query) before declaring CI green or broken avoids both false-negative and premature-done calls.
- Gating a "no data" vs "real zero" UI distinction on a sample-count signal (rows present?) rather than an incidental nil from an averaging query keeps both derived tiles reading from one coherent source of truth.

### What could've been better
- wk-self-review: a staged pending review is silently orphaned when the PR's base branch merges and the host auto-rebases the child onto the new base (new SHAs) — treat a base-merge-triggered rebase exactly like a force-push (delete + re-anchor the pending review), not only an explicit self-initiated force-push.
- wk-gh: the status-check rollup's head-ref OID can lag the actual pushed tip, so a single rollup read (or a `--watch` exit) can report a stale build for the prior commit — confirm the rollup's head matches the pushed ref before trusting its state.
- wk-pr: after adding a helper method exposed to views in a repo with generated type-signature artifacts, regenerate that artifact before pushing — the CI verify step fails on the stale generated file otherwise; fold it into the CI-fix loop's known-causes.
